# Exercise media

## Architecture

Five pieces, in the order the app loads them:

| File | Role |
| --- | --- |
| `assets/exercise-illustrations/manifest.json` | The approved first-party illustration library: canonical name, filename, intrinsic size, byte length and sha256 per image. |
| `exercise-media-catalog.js` | Legacy third-party art (Everkinetic), exact-name mapping. Unchanged. |
| `exercise-registry.js` | **Generated.** Canonical exercise per movement: id, name, aliases, equipment, muscles, pattern, `mediaId`. |
| `exercise-media-manifest.js` | **Generated.** One record per media asset: id, tier, style version, status, layout, thumbnail, start, finish, motion, cues, attribution. |
| `exercise-media-resolver.js` | Resolves a name to the best allowed media and reports which tier answered. |

`exercise-registry.js` and `exercise-media-manifest.js` are generated by
`tools/build-exercise-registry.mjs` and committed. Never hand-edit them — they are rebuilt
from the workout definitions plus the illustration manifest, so they cannot drift from the
exercises they describe.

## Coverage

**85 / 85 canonical exercises resolve to an approved first-party illustration at tier 1.**
No canonical exercise is served a substitution, a schematic, or a "coming soon" card.

## The approved illustration library

Each file in `assets/exercise-illustrations/` is one **composite**: a single wide image holding
the start, midpoint and finish of the movement side by side, with its phase labels burned into
the artwork. WebP, max dimension 960 px, ~22 KB each, 1.8 MB for the set.

That shape drives two rules in the renderers:

- The record sets `layout: "composite"`, `finish: null` and a single-entry `motion`, so the
  media layer sees **one** frame. A composite must never be fed to the two-position cross-fade
  demo — it would show the same picture twice and label the halves "Start" and "Finish".
- The card renders it full-width at its intrinsic aspect ratio, with no phase caption of its
  own, and links to the full-size image. Three panels inside a 260 px square would be unreadable
  on a phone, so tap-to-enlarge is part of the design rather than a nicety.

Integrity is enforced three times over, because a silently swapped or truncated asset is worse
than a missing one: `tools/build-exercise-registry.mjs` verifies every checksum before it will
generate, `scripts/build-web.mjs` verifies again before an image reaches `web-dist`, and
`tests/exercise-visuals.test.js` verifies the bytes are a real WebP of the declared length.

## Fallback hierarchy

`IronSixMediaResolver.resolve(name)` returns `{tier, tierName, media, label, via, provisional}`:

| Tier | Meaning | Labelled in UI |
| --- | --- | --- |
| 1 | First-party Iron Six illustration, exact movement | No (all approved) |
| 2 | Approved legacy media, exact movement | No |
| 3 | Alias-matched exact media | No |
| 4 | Approved canonical variation (same pattern **and** same equipment) | **Yes** — names the substitute |
| 5 | Approved movement-pattern reference | **Yes** — names the substitute |
| 6 | "Demo coming soon" | n/a |

The rule that matters: **tiers 4 and 5 may substitute a different movement, but never
silently.** The card names what it is actually showing. `tests/exercise-media-coverage.test.js`
fails if a substituted asset is rendered without a label naming its source movement.

Tiers 2–6 are currently unreachable for canonical exercises and remain in place for
coach-suggested movements the workout builders never program — the equipment-expansion library
in `api/equipment-exercises.js` still resolves through them.

A tempo or paused variant reuses the standard movement's illustration and says so on the card.

Supersets resolve each half independently; one half never stands in for the other.

## Adding an exercise

1. Add the movement to the workout builder as usual.
2. Produce an illustration for it and add a row to
   `assets/exercise-illustrations/manifest.json` with the **exact** canonical name, the
   filename, its pixel dimensions, byte length and sha256.
3. `node tools/build-exercise-registry.mjs`
4. `npm test`

Skipping step 2 is caught twice. The generator refuses to run if an illustration names a
movement the app does not program, or if the registry ends up pointing at a media record that
does not exist. And a new exercise that lands on tier 6 fails
`tests/exercise-media-coverage.test.js`, whose baseline in
`reports/media-coverage-baseline.json` now records 85 exact and an empty backlog — so any
regression away from full coverage fails the build. Regenerate that file with
`node tools/build-coverage-baseline.mjs` only after coverage genuinely improves.

## Audit

`node tools/exercise-audit.mjs` writes `reports/exercise-media-audit.json` and `.md`: every
exercise the app can show, its coverage bucket, broken references, orphan assets and duplicate
names that should collapse to one canonical movement.

The audit resolves through `exercise-media-resolver.js`, the same path the app uses. It
previously read the legacy catalogue directly, which predated the resolver — so when
first-party art landed it reported every approved illustration as "missing" because the
catalogue had never heard of it.

Names it reports as missing are equipment-expansion candidates from
`api/equipment-exercises.js`, not canonical exercises. Those render the labelled
"demo coming soon" card, which is the honest state for a movement with no art.

## Previous first-party art

The library replaces `ironsix-schematic-v1`, a generated 2D schematic rig under
`tools/exercise-art/`. Those SVGs are gone from `assets/`; the pose data and the form cues
remain in `tools/exercise-art/` because the cues are still carried onto the approved records by
movement name. The `schematic` status and its *"illustration in progress"* label are no longer
produced by the generator, and `tests/exercise-visuals.test.js` fails if any record reappears
with that status.
